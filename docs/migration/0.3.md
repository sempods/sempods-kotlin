# Moving from 0.2 to 0.3

## Operator actions

**The pod server needs `SEMPODS_SECRET_KEY`.** It encrypts the PKCE verifier of every sign-in in
flight. Without it the server does not start. Set the same key on every replica:

```bash
SEMPODS_SECRET_KEY=$(openssl rand -base64 32)
```

Changing the key later fails only the sign-ins in flight. A local run sets
`SEMPODS_DEV_SECRET_KEY_FALLBACK=true` instead, as
[`local.example.env`](../../deployments/local/env/local.example.env) does; with `PRODUCTION=true`
that setting fails the boot.

Sign-ins started before the upgrade, at the pod server and at the hosted MCP service, fail and have
to be started again. So does every sign-in that starts on a node of one version and returns to a
node of the other while both run side by side. The hosted MCP service needs no new setting: it keeps using
`MCP_SECRET_KEY`.

## Code changes

| 0.2 | 0.3 |
|---|---|
| `org.sempods.mcp.crypto.SecretCipher` | `org.sempods.auth.core.SecretCipher`, in `sempods-auth-core`. Same `v1:` envelope, so stored rows stay readable. `SecretCipher.fromEnv` is `McpSecretKey.cipherFromEnv` |
| `org.sempods.mcp.auth.LoginCsrfPin` | `org.sempods.commons.ktor.auth.BrowserPinCookie` for the cookie; `org.sempods.auth.core.BrowserSignIn` mints and compares the pin |
| A sign-in written around `OidcRelyingParty` | `BrowserSignIn`, which also checks `iss` (RFC 9207) |
| `OidcProviderMetadata(issuer, authorizationEndpoint, tokenEndpoint, jwksUri)` | an optional fifth argument, `authorizationResponseIssParameterSupported` |
| `PendingLogin.pod`, `.codeVerifier`, `.nonce`, `.browserPin` | gone; `BrowserSignIn` keeps the round trip |
